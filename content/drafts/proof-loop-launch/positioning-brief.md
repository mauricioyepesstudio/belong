## 1. Who this is for

Per `docs/PRODUCT_VISION.md` → Target Users table, six segments, each with a distinct build goal and core need:

| Segment | Build goal | Core need | Proof Loop angle |
|---|---|---|---|
| Founders | Startup | Co-builders, community, project hub | Turn a claim ("we can build X") into a Challenge others can join or contest |
| Professionals | Career | Mentors, events, accountability | Public commitments with deadlines create real accountability, not vague intentions |
| Learners | Learn | Communities, structured progress | Structured claim → evidence → outcome mirrors how real learning is validated |

Onboarding already captures **build goal** and **vision** (`docs/PRODUCT_VISION.md` line 51) — Proof Loop messaging should map directly onto whichever build goal a prospective user identifies with, not a single generic pitch.

## 2. The core hook: "Prove It"

Grounded directly in `BELONG_PROOF_LOOP.md`'s brand principle:

> Aura is what people think you are.
> Proof is what you've actually done.

This is the differentiator versus generic social feeds, and it should be used almost verbatim (it is already brand-approved language, not an invented tagline). The contrast to lead with:

- **Generic feeds** reward performance — content that generates reactions regardless of whether anything happened.
- **BELONG's Proof Loop** asks a different question first: *what would count as evidence that this is true, or that this got done?* (`BELONG_PROOF_PROTOCOL.md` §1)
- The product does not adjudicate who's "right" ideologically or morally — it resolves whether a *specific, predeclared claim* was supported, not supported, mixed, or inconclusive (`BELONG_PROOF_LOOP.md`, Outcome; `BELONG_PROOF_PROTOCOL.md` §6). This is a meaningfully different, more honest promise than "go viral" or "win the argument."
- The loop itself is nameable and demoable in copy: **CREATE → PROVE IT → DEFINE → CHALLENGE → APPROACH → SHOW UP → BUILD → EVIDENCE → OUTCOME → IMPACT → SHARE** (`BELONG_PROOF_LOOP.md`, "The end-to-end loop"). For launch copy, the compressed cultural version is cleaner: **PROVE IT → SHOW UP → BUILD → IMPACT → BELONG**.

Guardrails the copy must respect (non-negotiable per source docs, not stylistic preference):

- Never imply BELONG scores a person's truthfulness, worth, or ideology — no "Aura score," "Truth score," or similar (`BELONG_PROOF_LOOP.md`, Brand principle + rule 2).
- Frame Challenges as testing *claims or solutions*, never attacking a person (`BELONG_PROOF_LOOP.md` rule 1; `BELONG_PROOF_PROTOCOL.md` §2, §13).
- Don't claim likes, followers, or virality are evidence of anything — this is an explicit anti-manipulation rule (`BELONG_PROOF_PROTOCOL.md` §14). Copy should actively distinguish BELONG from platforms where they are.
- "Inconclusive" and "not supported" are legitimate, non-shameful outcomes — don't write copy that implies every Proof "wins" (`BELONG_PROOF_LOOP.md` rule 7; `BELONG_PROOF_PROTOCOL.md` §6).

## 3. Lead-generation angles (draft only — no execution)

Three angles appropriate for a pre-revenue, pre-traction social/collaboration platform. All are **suggestions for human evaluation**, not commitments — none of these have been contacted, scheduled, or budgeted.

### Angle A — Use the three V1 demo scenarios as PR/story hooks, not ad claims
`BELONG_PROOF_LOOP.md` → "V1 demo scenarios" explicitly names three seeded demo presentations built for V1: (1) five creators mobilizing 10,000 meals in 48 hours, (2) twenty founders creating 100 jobs in Miami in 30 days, (3) a cross-partisan Bridge project. These are documented as **demo/seeded presentation**, not resolved real-world outcomes — the doc is explicit that "production paths" stay on real data while these are presentation scaffolding for explaining the category.
- Usable as: "here's what a Proof looks like in practice" walkthroughs for press, a launch video script, or an explainer landing-page section.
- **Not usable as:** a claim that 10,000 meals were delivered, 100 jobs were created, or any Bridge project actually completed. Copy must clearly label these as illustrative/demo scenarios, not reported outcomes, or it becomes a fabricated metric.

### Angle B — Community partnerships tied to each Target User segment
Because `docs/PRODUCT_VISION.md`'s Target Users table already names six concrete segments with real needs (founder communities, career-mentor networks, learning cohorts, creator collectives, community-org networks, and general accountability/support groups), a natural pre-revenue lead channel is offering a small number of aligned community leaders (segment: "Community leaders" itself) early access to open the first real Challenges in their space — e.g., a founder accelerator opening a hiring/traction Challenge, or a mentorship community opening an accountability Commitment. This produces genuine first-party Proof Loop activity to reference later (once it happens) instead of needing to fabricate numbers now.
- Draft-stage output only: a partner outreach one-pager and a short partner pitch deck outline — not the outreach itself.

### Angle C — "Prove It" as an owned narrative hook for founder-led content
The brand principle (Aura vs. Proof) and the product verbs (BELIEVE / SHOW ME / PROVE IT / CHALLENGE / SHOW UP / BUILD / VERIFY / SHARE PROOF) are distinctive enough to support a recognizable content series — e.g., short posts or a newsletter format built around "here's a claim, here's what would prove it," using the founder's own commitments as the first real (not simulated) Proofs on the platform. This is lower-risk than paid acquisition because it doesn't require any traction numbers — it demonstrates the mechanic using the founder's own real activity.

All three angles require human decisions on channel, spend, partner selection, and timing before any step is taken (see below).

## 4. What NOT to claim yet

The repository contains **no reported user, retention, revenue, or usage metrics** for Proof Loop or BELONG generally. `docs/PRODUCT_VISION.md`'s Success Metrics table (Activated builders, Weekly builders, Mission clarity, Network density, Retention) defines *what will eventually be measured* — it is a framework, not a reported result. `docs/ROADMAP.md` confirms tests, CI/CD, and analytics (PostHog/Amplitude) are not yet built (Phase 3 / Phase 6, both unstarted per the Current State Summary), meaning there is no current instrumented way to produce real usage numbers even internally.

Do not, in any draft or future copy:
- State or imply any number of users, sign-ups, waitlist size, communities, Proofs created, Challenges resolved, meals delivered, jobs created, or dollars raised. None of these exist in this repo.
- Present the three demo scenarios (Angle A) as completed real-world outcomes.
- Imply Proof Loop has "gone live" broadly until a human confirms actual deployment state (see the ROADMAP.md discrepancy noted in §0).
- Use urgency/scarcity framing ("only X spots left," countdowns) — this is explicitly a non-goal per CLAUDE.md and `docs/PRODUCT_VISION.md` Non-Goals ("engagement bait").
- Frame Proof/Challenge mechanics in crypto, token, or points-economy language — explicit non-goal (`docs/PRODUCT_VISION.md` Non-Goals; CLAUDE.md).
- Use generic CRM/enterprise sales language — explicit non-goal (`docs/PRODUCT_VISION.md` Non-Goals; CLAUDE.md).
- Claim or imply BELONG scores truth, worth, or ideology — explicit brand rule (`BELONG_PROOF_LOOP.md`).
